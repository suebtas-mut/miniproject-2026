## 1. ขอบเขตระบบ (System Boundary)

ระบบประกอบด้วย 3 ส่วน ทำงานร่วมกันเป็นระบบเดียว

| ส่วน | เทคโนโลยี | หน้าที่ |
|---|---|---|
| **Client** | Flutter (Android / แท็บเล็ต) | หน้าจอทั้งหมดของ 4 บทบาท (Single App) |
| **Backend** | Node.js 20 + Express 4 + `node-oracledb` 6 (Thin Mode) | REST API · Business Logic · RBAC |
| **Database** | Oracle Database 21c XE (Docker) | เก็บข้อมูลหลัก + Transaction + Locking |

### 1.1 อยู่ในขอบเขต ✅
- ระบบ Master File: พนักงาน, แผนก, ตำแหน่ง, Role, Permission
- ระบบสิทธิ์แบบ Dynamic (เพิ่ม/ลบ/แก้สิทธิ์ได้ตลอดเวลา)
- ระบบหน้า Front: เส้นทาง, จุดจอด, รอบเวลา, รถ, คนขับ
- ระบบการจองรถ + QR Code + ยกเลิก
- ระบบสำหรับคนขับรถ: ตารางงาน, เริ่มงาน, Manifest, สแกน QR, ปิดงาน
- รายงาน **3 ข้อ**: R1 + R4 + R6

### 1.2 อยู่นอกขอบเขต ⛔
| สิ่งที่ตัดออก | เหตุผล |
|---|---|
| **Web Application (React)** | ข้อ 17.0 — ทีมตกลงใช้ Flutter อย่างเดียว ตรวจสอบช่องว่างแล้ว: ไม่มีโฟลเดอร์ `frontend-web/` |
| SADT / IDEF0 / Petri Net | เทคนิคเกินเกณฑ์ Mini Project |
| รายงาน R2, R3, R5, R7 | ข้อกำหนดให้เลือก 3 ข้อ (1 จากแต่ละกลุ่ม) · ทีมเลือก R1 + R4 + R6 |
| CORS configuration | ไม่มี Web Origin |
| โปรแกรมทำทุก Master File | ข้อกำหนดอนุญาตให้ insert ข้อมูลตรงจากฐานข้อมูลได้ (UC ก.7) |

## 4. Use Case Specification

> รูปแบบย่อย: **ผู้กระทำ · Precondition · Main Flow · Alternative Flow · Postcondition · Business Rule · ข้อผิดพลาด**

### 4.1 ระบบสิทธิ์และการเข้าสู่ระบบ (M3)

---

#### UC-01 เข้าสู่ระบบ (Login)

| หัวข้อ | รายละเอียด |
|---|---|
| **ผู้กระทำ** | Admin, Staff, Customer, Driver |
| **Precondition** | มีบัญชีในตาราง `employee` และสถานะ = `ACTIVE` |
| **Main Flow** | 1. ผู้ใช้กรอก **รหัสพนักงาน** + **รหัสผ่าน**<br>2. ระบบตรวจสอบรหัสผ่าน (เทียบกับ **bcrypt hash**)<br>3. ระบบอ่าน Role และ Permission ทั้งหมดของผู้ใช้<br>4. ระบบสร้าง **JWT** (อายุ 1 ชั่วโมง) เก็บ `jti` ไว้<br>5. ระบบคืนค่า `token` + `profile` + `permissions[]`<br>6. แอปสร้างเมนูตาม `permissions[]` → UC-04 |
| **Alternative Flow** | **2a.** รหัสผ่านผิด → ขึ้น "รหัสผ่านไม่ถูกต้อง" (ไม่บอกว่ามีบัญชีหรือไม่ ป้องกัน Brute Force)<br>**2b.** บัญชีถูกระงับ → ขึ้น "บัญชีถูกระงับการใช้งาน" |
| **Postcondition** | ผู้ใช้อยู่ในสถานะ `AUTHENTICATED` · มี JWT ที่ยังไม่ถูก blacklist ใน `token_blacklist` |
| **Business Rule** | BR-**M3-1** Password เก็บเป็น hash เท่านั้น ห้ามเก็บ plain text<br>BR-**M3-2** JWT หมดอายุ 1 ชม. · ตรวจสถานะ `jti` กับ `token_blacklist` ทุกครั้งที่เรียก API |
| **ข้อผิดพลาด** | `401 Unauthorized` · `423 Account Locked` |
| **Endpoint** | `POST /auth/login` · `GET /auth/me` |

---

#### UC-02 ออกจากระบบ (Logout)

| หัวข้อ | รายละเอียด |
|---|---|
| **ผู้กระทำ** | ทุกบทบาท |
| **Precondition** | ผู้ใช้ Login แล้ว |
| **Main Flow** | 1. ผู้ใช้กด "ออกจากระบบ"<br>2. ระบบเพิ่ม `jti` ของ token ลงตาราง `token_blacklist`<br>3. ระบบล้าง token ออกจากเครื่อง (`flutter_secure_storage`)<br>4. กลับหน้า Login |
| **Postcondition** | Token เดิมใช้ไม่ได้อีก (แม้ยังไม่หมดอายุ) |
| **Business Rule** | BR-**M3-3** Blacklist เก็บ `jti` ไว้จนกว่า token จะหมดอายุจริง (เก็บ `expires_at` เพื่อล้างข้อมูลเก่า) |
| **Endpoint** | `POST /auth/logout` |

---

#### UC-03 เปลี่ยนรหัสผ่าน

| หัวข้อ | รายละเอียด |
|---|---|
| **ผู้กระทำ** | ทุกบทบาท |
| **Precondition** | Login แล้ว · จำรหัสผ่านเดิมได้ |
| **Main Flow** | 1. กรอกรหัสผ่านเดิม → รหัสผ่านใหม่ → ยืนยันรหัสผ่านใหม่<br>2. ระบบตรวจรหัสผ่านเดิม<br>3. ระบบตรวจความยาว/ความซับซ้อนของรหัสผ่านใหม่<br>4. บันทึก hash ใหม่ · เพิ่ม `jti` เดิมลง blacklist |
| **Alternative Flow** | **3a.** รหัสผ่านใหม่อ่อน → แจ้งข้อกำหนด (≥ 8 ตัว, มีตัวใหญ่/เล็ก/เลข)<br>**3b.** รหัสผ่านใหม่ 2 ช่องไม่ตรง → ให้กรอกใหม่ |
| **Postcondition** | รหัสผ่านเดิมใช้ไม่ได้ · ต้อง Login ใหม่ |
| **Endpoint** | `POST /auth/change-password` |

#### UC-04 โหลดสิทธิ์และสร้างเมนูตามสิทธิ์

| หัวข้อ | รายละเอียด |
|---|---|
| **ผู้กระทำ** | ทุกบทบาท |
| **Precondition** | Login สำเร็จ (UC-01) |
| **Main Flow** | 1. แอปเรียก `GET /auth/me`<br>2. Backend รวม `permissions[]` จาก Role ทุกตัวของผู้ใช้<br>3. แอปสร้างเมนู: มือถือ → `NavigationBar` ล่าง / แท็บเล็ต (≥ 720 px) → `NavigationRail` ซ้าย |
| **Postcondition** | เมนูแสดงเฉพาะรายการที่ผู้ใช้มีสิทธิ์ |
| **Business Rule** | BR-**M2-1** เมนูสร้างจากข้อมูลสิทธิ์ในฐานข้อมูล **ล้วน** ไม่ hardcode รายการเมนู<br>BR-**M2-2** เมื่อ Admin ถอดสิทธิ์ → ผู้ใช้ที่ออนไลน์อยู่เห็นเมนูหาย **ทันที** (ตรวจสิทธิ์ทุก request ไม่ใช่ตอน login ครั้งเดียว) |

#### UC-05 ตรวจสิทธิ์การเข้าถึง (RBAC Middleware)

| หัวข้อ | รายละเอียด |
|---|---|
| **ผู้กระทำ** | ทุกบทบาท (ทำงานอัตโนมัติ ไม่มี UI) |
| **Precondition** | มี JWT ที่ยังไม่หมดอายุและไม่อยู่ใน blacklist |
| **Main Flow** | 1. Middleware ถอด JWT → ได้ `user_id`<br>2. Query `Role ↔ Permission` ของผู้ใช้จากฐานข้อมูล<br>3. ตรวจว่า `permission` ของ endpoint อยู่ในชุดสิทธิ์หรือไม่<br>4. อนุญาต → ส่งต่อไป Controller |
| **Alternative Flow** | **3a.** ไม่มีสิทธิ์ → `403 Forbidden` |
| **Postcondition** | — (Read-only) |
| **Business Rule** | BR-**M2-3** ⛔ ห้ามเขียน `if (role === 'admin')` · ห้าม hardcode รายชื่อ Role/Permission ในโค้ด · ต้องอ่านจากตารางทุกครั้ง |
| **จุดที่ต้องระวัง** | เป็นจุดที่อาจารย์ถามบ่อยที่สุด → ต้องมี Test Case พิสูจน์ว่าถอดสิทธิ์แล้วเมนูหายจริง (Sprint 5 DoD) |

### 4.2 ระบบจัดการพนักงาน (Master 1 — M1)

#### UC-06 จัดการข้อมูลพนักงาน (เพิ่ม / แก้ไข / ลบ)

| หัวข้อ | รายละเอียด |
|---|---|
| **ผู้กระทำ** | Admin |
| **Precondition** | Login แล้ว · มีสิทธิ์ `EMPLOYEE.*` |
| **Main Flow — เพิ่ม** | 1. Admin เลือกแผนก + ตำแหน่ง + กรอกรหัสพนักงาน/ชื่อ/อีเมล/เบอร์โทร<br>2. เลือก Role (ได้มากกว่า 1)<br>3. ระบบตรวจ: รหัสพนักงานซ้ำหรือไม่ · email ซ้ำหรือไม่ · แผนก/ตำแหน่งมีอยู่จริง<br>4. บันทึก `employee` + `employee_role`<br>5. ระบบแสดงพนักงานใหม่ในตาราง |
| **Main Flow — แก้ไข** | 1. Admin เลือกพนักงานจากตาราง<br>2. แก้ไขข้อมูล/แผนก/ตำแหน่ง/Role<br>3. ระบบตรวจความถูกต้อง → บันทึก |
| **Main Flow — ลบ** | 1. Admin เลือกพนักงาน → กดลบ → ยืนยัน<br>2. ระบบตรวจว่าพนักงานคนนั้นมีอะไรผูกอยู่ |
| **Alternative Flow** | **3a.** รหัสพนักงานซ้ำ → `409 Conflict` + ระบุว่าซ้ำกับใคร<br>**2a (ลบ).** พนักงานมี `booking` ในอดีต → ⛔ ห้ามลบจริง ให้เปลี่ยนสถานะเป็น `INACTIVE` แทน (เก็บประวัติให้รายงาน R3 ตรวจสอบย้อนหลังได้) |
| **Postcondition** | `employee` และ `employee_role` สอดคล้องกัน · ไม่มีพนักงานค้างสถานะ `INACTIVE` ที่ยัง login ได้ |
| **Business Rule** | BR-**M1-1** ทุกพนักงานต้องมี **แผนก** และ **ตำแหน่ง** (NOT NULL)<br>BR-**M1-2** รหัสพนักงานและอีเมลต้อง Unique<br>BR-**M1-3** พนักงานที่มี Booking ในอดีต → ลบไม่ได้ ใช้ `INACTIVE` แทน<br>BR-**M1-4** พนักงานที่ถูกมอบหมายเป็นคนขับในรอบที่ยังไม่จบ → ลบ/ระงับไม่ได้ |
| **ข้อผิดพลาด** | `409` รหัส/อีเมลซ้ำ · `422` ข้อมูลไม่ครบ |
| **Endpoint** | `GET/POST /employees` · `PUT/DELETE /employees/:id` · `GET/POST /departments` · `GET/POST /positions` |

#### UC-07 จัดการข้อมูลแผนก และ UC-08 จัดการข้อมูลตำแหน่ง

| หัวข้อ | รายละเอียด |
|---|---|
| **ผู้กระทำ** | Admin |
| **Precondition** | Login แล้ว · มีสิทธิ์ `DEPARTMENT.*` / `POSITION.*` |
| **Main Flow** | 1. เปิดหน้าแผนก/ตำแหน่ง (DataTable + Form)<br>2. เพิ่ม / แก้ไข / ลบ<br>3. ระบบตรวจชื่อซ้ำ → บันทึก |
| **Alternative Flow** | **3a.** ชื่อซ้ำ → `409 Conflict`<br>**2a (ลบ).** มีพนักงานใช้แผนก/ตำแหน่งนั้นอยู่ → `409` + ให้ย้ายพนักงานออกก่อน |
