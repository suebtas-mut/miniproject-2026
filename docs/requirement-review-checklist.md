### ข.3 ตารางข้อมูลที่ต้องเพิ่มเพื่อ "ให้รายงานทำได้"

> ⚠️ **ปัญหาสำคัญที่พบจากการรีวิว**
> ข้อกำหนดสั่งให้สร้างรายงาน 1–7 แต่ **ไม่ได้ระบุว่าต้องเก็บข้อมูลอะไรเพื่อให้รายงานนั้นทำได้**
> ถ้าไม่เพิ่มตารางเหล่านี้ รายงานจะทำไม่ได้หรือได้ตัวเลขไม่ตรง

| รายงาน | ต้องเก็บ/เชื่อมโยงอะไร | ตารางที่ต้องมี |
|---|---|---|
| R1 คนขึ้น/ลงรายสัปดาห์ | จำนวนผู้โดยสารที่ **ขึ้นจริง** และ **ลงจริง** แยกกัน | `trip` + `trip_passenger` (board_seq, alight_seq, alight_time) |
| R2 สถิติรายปี | จำนวนจอง / ที่นั่งที่จอง / ยกเลิก / Check-in สำเร็จ / No Show | `booking` (status ครบ 5 สถานะ) + `trip_passenger.checkin_time` |
| R3 พฤติกรรมราย user | จอง / ขึ้นจริง / ยกเลิก / No Show รายบุคคล | `booking.cust_id` + `status` |
| R4 ผู้ใช้รายวันรายเส้นทาง | จำนวน Booking ต่อ เส้นทาง × วัน | `booking` + `schedule` (service_date, route_id) |
| R5 ขึ้น/ลงรายจุดจอดตามเวลารถออก | เวลาที่รถถึงแต่ละจุด + จำนวนขึ้น/ลงจริง | `schedule_stop` (arrive_time) + `trip_passenger` (board_seq / alight_seq) |
| R6 รอบงานคนขับ ก่อน/หลัง 17:00 | คนขับ + เวลาออกของรอบ | `driver_assign` + `schedule.depart_time` |
| R7 รอบต่อรถ / ประเภทรถ | รถ → ประเภทรถ → ที่นั่ง + จำนวนรอบที่ถูกใช้ | `vehicle` + `vehicle_type` + `vehicle_assign` |

**สรุป:** ต้องมีตารางเพิ่มอย่างน้อย 2 ตาราง คือ **`trip`** (การเดินรถจริง) และ
**`trip_passenger`** (รายละเอียดผู้โดยสารรายคนต่อรอบ) ไม่งั้น **R1** ทำไม่ได้
ส่วน **R6** ใช้ `driver_assign` + `schedule.depart_at` ที่มีอยู่แล้ว → ไม่ต้องเพิ่มตาราง

### ข.4 Non-Functional Requirements ที่ควรเพิ่ม

| หัวข้อ | เป้าหมายที่ควรใส่ |
|---|---|
| Performance | API ตอบ < 500 ms, รายงาน (ข้อมูล 50,000 แถว) < 3 วินาที |
| Concurrent Users | รองรับ ≥ 200 คนพร้อมกัน |
| Security | Password เป็น hash, ใช้ Parameterized Query, JWT, HTTPS |
| Availability | ใช้งานได้ในเวลาราชการ 99% |
| Usability | ผู้ใช้จองสำเร็จภายใน 5 คลิก |
| Maintainability | แยก Module, มีเอกสาร, Unit Test Coverage ≥ 60% |
| Scalability | รองรับข้อมูล 100,000 การจอง |

### ข.5 สิ่งที่ควร "ไม่ต้องทำ" (ประหยัดเวลา)
